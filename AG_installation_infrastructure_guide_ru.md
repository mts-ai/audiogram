# Об этом документе

Audiogram – это продукт микросервисной архитектуры от компании ООО «МВС ИИ», который выполняет следующие функции:
- распознавание речи в потоковом и/или файловом режимах;
- отложенное распознавание речи;
- синтез речи в потоковом и/или файловом режимах;
- клонирование голоса.

В этом документе представлены требования и инструкции по подготовке инфраструктуры для установки полной версии Audiogram.

# Требования к DevOps-инженерам

Подготовку инфраструктуры для развертывания Audiogram необходимо выполнять DevOps-инженерам со следующими компетенциями:
- опыт администрирования Linux;
- опыт развертывания и поддержки решений микросервисной архитектуры;
- навыки работы с Kubernetes и helm;
- навыки работы с Apache Kafka, Apache Superset, PostgreSQL, KeyDB, ClickHouse, Keycloak, S3-совместимыми хранилищами.

# Структура Audiogram

Чтобы лучше понимать процесс установки Audiogram, в первую очередь стоит разобрать его структуру.

Audiogram состоит из 5 модулей:

| **№** | **Название модуля** | **Описание** | 
| ------ | ------- | ----- |
| 1 | asr | Содержит микросервисы, отвечающие за распознавание и отложенное распознавание речи. | 
| 2 | tts | Содержит микросервисы, отвечающие за синтез речи. | 
| 3 | common | Содержит микросервисы, которые используются микросервисами других модулей. | 
| 4 | media | Содержит микросервисы, отвечающие за работу архива, в котором хранятся аудиоданные, поступившие в запросе на распознавание речи, результаты распознавания, а также метки и данные других микросервисов модуля asr. | 
| 5 | iam | Содержит микросервисы, отвечающие за аутентификацию и авторизацию пользователей. |

> Для промышленного использования все микросервисы, входящие в состав Audiogram, должны быть установлены в Kubernetes-кластере.
Во время работы некоторые микросервисы обращаются к различным базам данных и к S3-совместимому хранилищу. Эти базы данных и хранилище должны быть развернуты снаружи Kubernetes-кластера.

### Инструкция по настройке клиента Keycloak для компонента admin-backend

Данная инструкция описывает процесс создания и конфигурирования OIDC-клиента в Keycloak версии 18.0.0. Настройка необходима для обеспечения корректной авторизации backend-сервиса и получения токенов с расширенным набором атрибутов (Claims).

#### Создание и базовая настройка клиента

Чтобы создать клиента, выполните следующие действия:
1. Перейдите в административную консоль Keycloak и выберите целевой **Realm**.
2. В левом боковом меню перейдите в раздел **Clients** и нажмите кнопку **Create client**.
3. В появившемся окне укажите:
   - **Client ID**: *admin-backend* (или иное имя согласно вашему стандарту)
   - **Client Protocol**: *openid-connect*
4.	Нажмите **Save**. Вы попадете на вкладку **Settings**. Установите следующие параметры:
    - **Access Type**: выберите *confidential* (это активирует секретный ключ клиента)
    - **Standard Flow Enabled**: *On* (разрешает стандартную авторизацию через браузер)
    - **Direct Access Grants Enabled**: *On* (разрешает обмен логина/пароля на токен напрямую)
    - **Service Accounts Enabled**: *On* (позволяет клиенту аутентифицироваться как сервису, без участия пользователя)
5.	Нажмите **Save** внизу страницы.

#### Настройка прав сервисного аккаунта (Service Account Roles)

Для того, чтобы backend мог управлять пользователями и клиентами через Keycloak API, необходимо назначить ему соответствующие привилегии:
1. Перейдите на вкладку **Service Accounts Roles**.
2. В выпадающем списке **Client Roles** выберите значение *realm-management*.
3. В блоке **Available Roles** выделите следующие роли и нажмите **Add selected**:
    - view-users
    - view-clients
4. Убедитесь, что выбранные роли переместились в блок **Assigned Roles**.

#### Настройка мапперов токена (Mappers)

Мапперы необходимы для добавления специфической информации в тело токена (Access Token и ID Token). Перейдите на вкладку **Mappers** и для каждого пункта нажмите **Create**.

##### Mapper: Realm name

- **Name**: *Realm name*
- **Mapper Type**: *Hardcoded claim*
- **Token Claim Name**: *realm*
- **Claim value**: *Укажите точное имя вашего Realm (чувствительно к регистру*).
- **Claim JSON Type**: *String*
- **Добавление в токены**: Установите *On* для **Add to ID token**, **Add to access token** и **Add to user info**.

##### Mapper: Client ID

- **Name**: *Client ID*
- **Mapper Type**: *User Session Note*
- **User Session Note**: *clientAddress*
- **Token Claim Name**: *clientAddress*
- **Claim JSON Type**: *String*
- **Добавление в токены**: Установите *On* для **Add to ID token** и **Add to access token**.

##### Mapper: Client Host

- **Name**: *Client Host*
- **Mapper Type**: *User Session Note*
- **User Session Note**: *clientHost*
- **Token Claim Name**: *clientHost*
- **Claim JSON Type**: *String*
- **Добавление в токены**: Установите *On* для **Add to ID token** и **Add to access token**.

##### Mapper: Client IP Address

- **Name**: *Client IP Address*
- **Mapper Type**: *Hardcoded claim*
- **Token Claim Name**: *realm (Внимание: убедитесь, что это поле соответствует вашим требованиям)*
- **Claim value**: *Укажите имя вашего Realm*
- **Claim JSON Type**: *String*
- **Добавление в токены**: Установите *On* для **Add to ID token**, **Add to access token** и **Add to user info**.

#### Конфигурация клиентских областей (Client Scopes)

Перейдите на вкладку **Client Scopes**, чтобы определить состав передаваемых данных.
1. В разделе **Default Client Scopes** (области, выдаваемые всегда) должны присутствовать:
   - *acr, email, profile, realm, roles, web-origins*.
2.	В разделе **Optional Client Scopes** (области, запрашиваемые параметром scope) должны присутствовать:
    - *address, microprofile-jwt, offline-access, phone*.

### Инструкция по настройке клиента Keycloak для компонента admin-frontend

Данная инструкция описывает процесс конфигурирования публичного OIDC-клиента в Keycloak версии 18.0.0. Настройка оптимизирована для работы фронтенд-приложений, требующих авторизации пользователей через браузер.

#### Создание и базовая настройка клиента

Чтобы создать клиента, выполните следующие действия:
1.	Перейдите в административную консоль Keycloak, выберите целевой **Realm**.
2.	В разделе **Clients** нажмите кнопку **Create client**.
3.	Установите базовые параметры:
    - **Client ID**: *admin-frontend* (идентификатор вашего веб-приложения).
    - **Client Protocol**: *openid-connect*.
4.	Нажмите **Save**. На вкладке **Settings** задайте следующие параметры безопасности и доступа:
    - **Access Type**: выберите *public*.
    > Примечание: Публичный тип используется, так как фронтенд-приложение не может безопасно хранить секретный ключ (Client Secret).
    - **Standard Flow Enabled**: *On* (активирует стандартный сценарий входа через форму Keycloak).
     - **Direct Access Grants Enabled**: *On* (позволяет приложению обменивать учетные данные пользователя на токены напрямую, если это предусмотрено архитектурой).

#### Настройка параметров безопасности (Redirects & CORS)

Для обеспечения безопасности перенаправлений и предотвращения ошибок кросс-доменных запросов (CORS), настройте следующие поля:
1.	**Valid Redirect URIs**: установите * (символ подстановки).
    > Рекомендация: Для продуктивной среды замените * на конкретный URL вашего фронтенда (например, https://admin.example.com*), чтобы исключить атаки через перенаправление.
2.	**Web Origins**: установите *.
    > Примечание: Это разрешает браузеру выполнять запросы к Keycloak из вашего приложения (CORS). В продуктивной среде рекомендуется указать конкретный домен приложения.
3.	Нажмите **Save**.

#### Настройка мапперов токена (Mappers)

Для того, чтобы фронтенд получал необходимую информацию о среде внутри токена, создайте маппер:

###	Рекомендации по настройке баз данных PostgreSQL

Как указано выше, подробную информацию по настройке баз данных PostgreSQL можно найти на сайте производителя. Однако, так как базы данных PostgreSQL находятся вне контура Kubernetes, необходимо уделить особое внимание сетевой доступности и правам доступа.

#### Требования к пользователям и безопасности	

Для работы сервиса через ORM (со стороны K8s) необходимо настроить две роли:
- **Администратор (Owner)**:
  -	Обладает правами ALL PRIVILEGES на базу данных. Используется для миграций верхнего уровня и обслуживания.
- **Сервисный пользователь (например, bi_user)**:
  - **Область видимости**: Права USAGE и CREATE на схему *public*.
  - **Операции (DML/DDL)**: Полный CRUD (SELECT, INSERT, UPDATE, DELETE), а также права на изменение структуры таблиц (ALTER), индексов и работу с последовательностями (USAGE, SELECT на SEQUENCES), что критично для ORM.
  - **Сетевой доступ**: В файле *pg_hba.conf* должен быть разрешен доступ для этого пользователя только из подсети Kubernetes-кластера (Node IP или Pod CIDR).

#### Отказоустойчивость и репликация

Для обеспечения High Availability (HA) вне Kubernetes рекомендуется классическая схема:
- **Топология**: Кластер из **3-х узлов** (Master + Hot Standby).
- **Механизм**: Потоковая репликация (Streaming Replication).
- **Управление отказоустойчивостью**: Зависит от нагрузки. При минимальной нагрузке допустимо использование **Keepalived** (VIP-адрес) для переключения между мастером и репликой или **Patroni** для автоматизации Failover. Если нагрузка средняя или высокая, уточните в документации PostgreSQL.
- **Backup**: Настройка ежедневных бэкапов на отдельное хранилище, так как базы находятся на внешних виртуальных машинах.

#### Сетевые требования

- **Порт**: По умолчанию 5432 (TCP).
- **Связность**: Между узлами Kubernetes и виртуальной машиной с БД должен быть открыт сетевой доступ (Security Groups/Iptables).
- **DNS**: Рекомендуется обращаться к базе по доменному имени (FQDN), а не по IP, чтобы упростить переключение на реплику при аварии.

#### Режим работы приложения

Взаимодействие производится на уровне CRUD с использованием транзакций через ORM.

Если нагрузка низкая, параметры *max_connections* можно оставить на стандартных значениях (100). Если нагрузка средняя или высокая, уточните в документации PostgreSQL.

###	Рекомендации по настройке KeyDB

Как указано выше, подробную информацию по настройке KeyDB можно найти на сайте производителя. Однако, так как базы данных KeyDB, следует обратить внимание на следующие моменты.

Рекомендуется использовать режим **Multi-Master (Active-Active)**. Это обеспечит высокую доступность: если одна виртуальная машина выйдет из строя, остальные продолжат принимать и запись, и чтение.
Ниже представлены советы по настройке кластера из 3-х узлов.

#### Подготовка инфраструктуры

- **Количество узлов**: 3 ВМ (для обеспечения кворума и отказоустойчивости).
- **Сетевые доступы**:
  - Открыть порт **6379** между всеми ВМ KeyDB (для синхронизации).
  - Открыть порт **6379** для подсети Kubernetes (для доступа микросервисов).
- **Рекомендуемые ресурсы**: Минимум 2 CPU, 4 ГБ RAM (зависит от объема кэшируемых данных).

#### Базовая настройка

На каждой виртуальной машине установите KeyDB и оптимизируйте параметры ядра для работы с памятью:

``` bash 
# Отключение Huge Pages (рекомендация для Redis/KeyDB)
echo never > /sys/kernel/mm/transparent_hugepage/enabled
# Увеличение лимита открытых файлов
ulimit -n 65535
```

#### Конфигурация KeyDB (/etc/keydb/keydb.conf)

Отредактируйте конфиг на каждом узле. Основные параметры, которые должны быть идентичны:

``` bash 
conf
# Сетевой интерфейс
bind 0.0.0.0
port 6379
protected-mode no

# Многопоточность (настройте под кол-во ядер вашей ВМ)
server-threads 2
worker-threads 2

# Режим Active-Active (Multi-Master)
active-replicate yes
multi-master yes

# Лимиты памяти (настройте под вашу ВМ)
maxmemory 2gb
maxmemory-policy allkeys-lru

# Сохранение данных на диск (Persistence)
appendonly yes
appendfsync everysec
```

#### Настройка связей (Peering)

Чтобы узлы видели друг друга, добавьте в конец конфига на каждом сервере адреса других узлов кластера.

##### На Узле 1 (10.0.0.1):


``` bash 
conf
replicaof 10.0.0.2 6379
replicaof 10.0.0.3 6379
```

##### На Узле 2 (10.0.0.2):


``` bash 
conf
replicaof 10.0.0.1 6379
replicaof 10.0.0.3 6379
```

##### На Узле 3 (10.0.0.3):


``` bash 
conf
replicaof 10.0.0.1 6379
replicaof 10.0.0.2 6379
```

#### Подключение из Kubernetes

Для микросервисов внутри кластера рекомендуется создать абстракцию, чтобы не прописывать IP-адреса ВМ в коде:
1.	Создайте **Service** типа **ExternalName** или **Endpoints** без селектора, указывающие на IP-адреса ваших ВМ.
2.	Используйте библиотеку с поддержкой балансировки (например, **Lettuce** для Java или **go-redis**), передав ей список всех трех IP.


##### Проверка статуса

После перезапуска сервиса (systemctl restart keydb-server) проверьте состояние репликации:

``` bash 
keydb-cli info replication
```

В выводе вы должны увидеть role:master и connected_slaves: 2. Поскольку включен multi-master, каждый узел считает себя мастером и видит остальных как реплики.

> **Примечание**: KeyDB в режиме Active-Active использует механизм **Last Write Wins** (побеждает последняя запись). Если ваши микросервисы одновременно обновляют один и тот же ключ на разных узлах, итоговым значением станет то, что пришло позже по метке времени.

#### Сетевая связность и Advertised Listeners

Это самый критичный этап для работы Kafka вне кластера. Брокеры должны сообщать клиентам (сервисам в K8s) свои **внешние IP или FQDN**.

- **Конфигурация server.properties**:

``` bash 
properties
# Внутренний интерфейс для обмена между брокерами
listeners=PLAINTEXT://0.0.0.0:9092
# Адрес, который брокер передаст клиенту (K8s/ClickHouse) для подключения
advertised.listeners=PLAINTEXT://://example.com
```

- **Порты**: Открыть TCP 9092 (или 9093 для SASL) для всей подсети Kubernetes и узлов ClickHouse.

#### Отказоустойчивость кластера

Для обеспечения высокой доступности (HA) и обработки нагрузки > 2000 RPS:

- **Топология**: Минимум **N=3 брокера**.
- **Кворум (Controller)**: Если используется **KRaft** (рекомендуется для новых инсталляций), необходимо 3 узла контроллеров. Если **Zookeeper** — ансамбль из 3 узлов на отдельных ВМ.
- **Параметры надежности**:
   - default.replication.factor: 3 (данные всегда на 3-х узлах).
   - min.insync.replicas: 2 (запись подтверждена, если хотя бы 2 узла синхронизированы).

#### Управление пользователями и ACL

Авторизация обязательна для разграничения доступа микросервисов и ClickHouse.

| **Роль** | **Ресурс** | **ACL операции** | **Назначение** |
| ------ | ------- | ----- |----- |
| admin | Cluster, Topic:, Group: | All | Полный доступ |
| migrator | Cluster, Topic:* | Create, Delete, Describe, Alter | Создание топиков сервисом миграций |
| data-writer | Topic:* | Write, Describe | Отправка данных из API и Агентов |
| clickhouse-reader | Topic:, Group: | Read, Describe | Вычитка данных в ClickHouse |

> **Важно**: Для clickhouse-reader права на Group обязательны, иначе ClickHouse не сможет фиксировать смещения (offsets).

#### Оптимизация под нагрузку (2000+ RPS)

- **Партиционирование**: Минимум **6-12 партиций** на каждый топик. Это позволит ClickHouse читать данные параллельно несколькими потоками.
- **Очистка данных (Retention)**: Установить log.retention.hours: 24 или 48. Данные в Kafka — это временный буфер, их долговременное хранение обеспечивается в ClickHouse.
- **Дисковая подсистема**: Рекомендуется использование **SSD** (NVMe) для минимизации задержек при записи (IOPS).

#### Динамическое управление

Так как топики создаются сервисом bi-migrations-service, в конфигурации брокеров должно быть:
auto.create.topics.enable: false — для строгого контроля структуры данных.

## Шаг 7 – Настройте ClickHouse

> **Требование к версии**: ClickHouse 25.10.2 или новее

Снаружи кластера настройте 1 базу данных ClickHouse.

За техническими требованиями и более подробной информацией обращайтесь к [документации ClickHouse](https://clickhouse.com/docs).

Сервисы Audiogram, которые используют базу данных ClickHouse:

| **Название сервиса** | **Модуль Audiogram, к которому относится сервис** |  
| ------ | ------- | 
| bi-migrations | common | 
| bi-superset | Это платформа (Apache Superset) для анализа и визуализации данных с открытым исходным кодом, которая является одним из инструментов реализации BI (business intelligence). Apache Superset необходимо скачать с [официального сайта производителя](https://superset.apache.org/) и установить вручную внутри или снаружи кластера (на усмотрение организации, выполняющей развертывание Audiogram). | 

DevOps-инженерам, которые будут проводить установку Audiogram в кластер, понадобятся адрес и название базы ClickHouse, а также логин и пароль пользователя с правами *read-write*.

### Рекомендации по настройке базы данных ClickHouse

Как указано выше, подробную информацию по настройке баз данных ClickHouse можно найти на сайте производителя. Однако, так как база данных ClickHouse находятся вне контура Kubernetes, необходимо уделить внимание следующим моментам.

#### Архитектура потока данных

Данные поступают в ClickHouse из **Apache Kafka** по следующей схеме:
1.	Сервисы пишут события в топики Kafka.
2.	В ClickHouse создаются таблицы с движком Kafka (Consumer), которые вычитывают сообщения.
3.	Материализованные представления (Materialized Views) перекладывают данные из Kafka-таблиц в целевые таблицы с движком ReplicatedMergeTree.

#### Требования к кластеру и репликации

Для обеспечения отказоустойчивости и обработки нагрузки (> 2000 RPS на запись) необходимо развернуть кластерную конфигурацию:
- **Топология**: Минимум **N=2 реплики** для каждого шарда.
   > Важное уточнение: ClickHouse не требует нечетного количества реплик для кворума данных (в отличие от ZooKeeper). Достаточно 2-х реплик для обеспечения доступности. Нечетное количество (минимум 3) строго обязательно только для узлов **ZooKeeper/ClickHouse Keeper**, которые управляют репликацией.
- **Движки таблиц**: Все таблицы должны создаваться с использованием префикса *Replicated* (например, *ReplicatedMergeTree*) и параметра *ON CLUSTER*.
- **Координация**: Необходим отказоустойчивый ансамбль **ClickHouse Keeper** (или ZooKeeper) из 3 узлов.

#### Управление пользователями и правами (RBAC)

Сервис миграций должен иметь права на управление кластером и создание пользователей для конечных витрин.

**Сервисный пользователь (migrator)**:

``` sql 
-- Управление базами и таблицами
GRANT CREATE DATABASE, DROP DATABASE, CREATE TABLE, DROP TABLE, ALTER, TRUNCATE ON *.* TO migrator;
-- Операции с данными
GRANT SELECT, INSERT, DELETE ON *.* TO migrator WITH GRANT OPTION;
-- Работа с очередями и движками
GRANT TABLE ENGINE ON Kafka TO migrator;
GRANT KAFKA ON *.* TO migrator;
-- Администрирование кластера и DDL
GRANT CREATE USER, CLUSTER, DISTRIBUTED DDL ON *.* TO migrator;
GRANT SYSTEM DROP CACHE ON *.* TO migrator;
```

#### Конфигурация интеграции с Kafka

Для аутентификации в Kafka на стороне всех узлов ClickHouse в конфигурационном XML (например, */etc/clickhouse-server/config.d/kafka.xml*) должны быть заданы параметры безопасности.

**Пример конфигурации**:

``` xml 
<clickhouse>
    <kafka>
        <security_protocol>sasl_plaintext</security_protocol>
        <sasl_mechanism>SCRAM-SHA-512</sasl_mechanism>
        <sasl_username>clickhouse-reader</sasl_username>
        <sasl_password from_env="KAFKA_PASSWORD"/>
        <session_timeout_ms>30000</session_timeout_ms>
        <max_poll_interval_ms>300000</max_poll_interval_ms>
        <!-- bootstrap_servers не указываем здесь, так как они задаются в DDL таблицы -->
    </kafka>
</clickhouse>
```

#### Сетевые требования и связность

Поскольку ClickHouse находится вне K8s:
- **Порты**: Должны быть открыты 8123 (HTTP), 9000 (Native protocol) и 9004 (Inter-server replication) для подсети K8s и между узлами кластера.
- **Служебный доступ**: Необходим доступ от ClickHouse до брокеров Kafka (порт 9092/9093) и до узлов Keeper (порт 2181/9181).

> **Рекомендация**: Так как планируется высокая нагрузка на запись (2000+ ops), убедитесь, что в ClickHouse настроена **запись пачками (batches)** через Materialized Views, чтобы избежать ошибки «Too many parts».
